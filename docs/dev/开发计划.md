## 0.12–0.13（已交付）：LPC 素材库 + 角色合成

这条线不在原计划里，是用户「我手上没素材，让你直接用 LPC 的部位」带出来的。
现在可以在插件里**从头拼一个完整角色**，不用离开窗口。

| 能力 | 说明 |
| --- | --- |
| 素材库 | 15 个类别、约 150 个部件，**只存路径不存图**，点击才从上游取 |
| 双层部件 | 马尾/披风/部分盾牌分 fg+bg 两层，自动成对取回 |
| 角色合成 | 分层叠加、按部位自动排序、手动偏移、单帧/多帧表都支持 |
| 自检 | 只有后层没有前层时直接报警，并可一键补上 |

**关键约束（法律）**：LPC 素材是 CC0 / CC-BY-SA / CC-BY / GPL 混合，多数强制署名。
插件不复制、不分发，只做「按需取回」，署名责任回到使用者 —— 界面上写明了。

**上游结构比想象乱**，这是踩出来的（详见 [踩坑记录.md](踩坑记录.md) 与迭代记录 0.11–0.13）：

- 同一动作的部位图尺寸一致（576×256 = 9 帧 × 4 向 × 64px），所以整表叠加即可对齐
- 目录层级不统一：`body/bodies/male/walk.png`、`hair/long/adult/walk.png`、
  `body/bodies/zombie/walk/zombie.png` 三种并存
- 有些部件没有动画文件（按颜色命名），库里只收能解的
- zPos 以 LPC `sheet_definitions` 为准（body 10 → torso 40 → hair 120 → weapon 140）

## 0.4 路线（四批资源调研后的排序，详见 [素材资源调研.md](素材资源调研.md)）

排序依据是「补哪个短板 × 成本 × 许可干净程度」，不是「哪个资源名气大」。

1. ✅ **无缝材质生成 + 平铺 / 滚动预览**（0.4.0 生成、0.8.3 滚动预览、0.9.0 补全双层与后处理）
   实际落地用的是**周期值噪声（晶格索引取模）**而不是 `simplex-noise` 的 4D 环面采样 ——
   零依赖、同样保证无缝，实测接缝跳变与内部同量级。抖动用的是 4×4 Bayer（比 RgbQuant 轻得多，
   够用）。补的是「造不出背景」这个最大缺口。
   剩下：多材质（砖/木/水）、第二层混合、画布上任意图的平铺预览。

2. ✅ **网格预设**（0.5.0 已交付）
   LPC 64 / 图集 32 / Kenney 18 / Kenney 16 四个尺寸预设，外加 LPC 的四个动作
   （突刺/行走/挥砍/坐下，行号取自生成器源码）。**只存参数、不存图**。
   附带做了四向命名与「跳过全空白格」，否则 LPC 13 列的表会切出一堆空帧。

3. ✅ **图集打包 + pivot 元数据**（0.6.0 已交付）
   货架式装箱（手写 40 行，客户端拿不到 npm）+ Aseprite 字段的 `atlas.json` + 可选锚点。
   输出走已有 ZIP 通道。补的短板一次两个：图集、锚点/脚底对齐。

4. **AI 生成走 MCP 连接器**（插件零改动）
   首选 Pixel Engine（OAuth 零 key + 100 credits/月免费）与 Retro Diffusion（$0.03/张、输出归你）。
   **不在插件里内置 key**：Retro Diffusion 的 ToS 明禁把 key 放进客户端，PixelLab 对「自建服务」要求先联系。
   插件侧只做一个「从工作区导入」的入口。

5. ✅ **动画预览**（0.7.0 已交付）
   按名字自然序排队、播放/暂停、8·12·24 fps、洋葱皮、帧条跳帧；所有帧底部居中对齐（脚底基准）。
   顺序不能用字符串比较 —— `hero_10` 会排到 `hero_2` 前面，所以单独写了 `compareNatural`。

**更远**：

- **存成工作区真实文件**（需要 Host 服务）：数据现在困在 IndexedDB，只能靠导出搬。
  先决条件是确认 bundle 形态能不能用 `host.call`（已安装的四个第三方插件都没用它）。
- **Agent 工具**：Host 注册 `sprite_slice`，让 Agent 也能切工作区里的图。
- **背景生成增强**：多材质（砖/木/水）、第二层不同周期混合（压重复感）、
  画布上任意图的平铺预览（现在只有生成面板里有）。

## 取舍备忘

- **为什么全放 Client**：0.1 的时间里，最大的不确定性是「bundle 形态能不能跟 Host 通信」，
  而不是「像素算法怎么写」。把不确定性砍掉，先交付一个真能用的工具；
  Host 一侧的持久化是增强项，随时可以加。
- **为什么用 DOM 而不是 `<canvas>` 画布**：拖动/命中/选中/无障碍都快得多，
  缩放手感也更稳（浏览器直接合成）。canvas 只在需要像素时用来离屏处理。
- **为什么存 dataURL 而不是 Blob**：工程 JSON 导出/导入零成本，`<img src>` 直接用，
  省掉 objectURL 的生命周期管理。代价是内存约 1.33×，对精灵图这个量级无所谓。
- **为什么撤销用快照而不是命令日志**：状态是不可变数组 + 字符串图片，
  一份快照就是几十个指针；命令日志要为每种操作写正反两套，容易漏。
- **为什么撤销不撤镜头**：撤销的语义是「撤我的编辑」，不是「撤我刚才看了哪里」。
- **为什么导出自己写 ZIP**：多文件下载会被浏览器拦；PNG 已压过，store 模式 + CRC32
  约 100 行，比引一个库可控，而且字节结构可以拿系统解压器验。
